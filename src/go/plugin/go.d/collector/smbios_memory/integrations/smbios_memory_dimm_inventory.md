# SMBIOS Memory (DIMM inventory)


<img src="https://netdata.cloud/img/microchip.svg" width="150"/>


Plugin: go.d.plugin
Module: smbios_memory

<img src="https://img.shields.io/badge/maintained%20by-Netdata-%2300ab44" />

## Overview

This collector exposes per-DIMM physical memory inventory from the system's BIOS/UEFI.

It reads the raw SMBIOS structure table (`/sys/firmware/dmi/tables/DMI`, the same data `dmidecode -t 17` reads) and decodes the SMBIOS Memory Device (DMI type 17) records. Unlike EDAC, which only reports memory devices that participate in error detection, SMBIOS provides the authoritative slot-by-slot inventory including DDR generation, manufacturer, and part number.

For each populated memory slot it reports the module size, configured speed, and rank count, and attaches the slot locator, bank locator, memory type (e.g. DDR4/DDR5), form factor, manufacturer, and part number as labels. Empty slots are skipped.


The collector parses the SMBIOS entry structures directly from the kernel-exported DMI table; it does not execute `dmidecode`.


This collector is only supported on the following platforms:

- Linux

This collector only supports collecting metrics from a single instance of this integration.

The raw DMI table (`/sys/firmware/dmi/tables/DMI`) is typically readable only by root. The Netdata Agent must be able to read this file for the collector to work.


### Default Behavior

#### Auto-Detection

This collector is disabled by default and must be explicitly enabled. Once enabled, it reads the configured DMI table path and starts if at least one Memory Device (type 17) record is present.


#### Limits

The default configuration for this integration does not impose any limits on data collection.

#### Performance Impact

Memory inventory is static hardware information, so a long collection interval (default 60 seconds) is sufficient and the exposed metrics do not churn.

### Prerequisites

#### Enable the collector

This collector is opt-in. Enable it by setting `smbios_memory: yes` in the `modules` section of `go.d.conf`.


#### Grant read access to the DMI table

Ensure the user running the Netdata Agent can read `/sys/firmware/dmi/tables/DMI`. This file is usually root-only, so read access must be granted explicitly.

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.



### Per memory module

These metrics refer to a single physical memory module (DIMM).

Labels:

| Label      | Description     |
|:-----------|:----------------|
| location | Device locator (physical slot), e.g. DIMM_A1. |
| bank_locator | Bank locator reported by the BIOS. |
| memory_type | Memory type, e.g. DDR4, DDR5. |
| form_factor | Module form factor, e.g. DIMM, SODIMM. |
| manufacturer | Module manufacturer. |
| part_number | Module part number. |

Metrics:

| Metric | Dimensions | Unit |
|:------|:----------|:----|
| smbios_memory.dimm_size | size | bytes |
| smbios_memory.dimm_speed | speed | MT/s |
| smbios_memory.dimm_ranks | ranks | ranks |



## Troubleshooting

### Debug Mode

**Important**: Debug mode is not supported for data collection jobs created via the UI using the Dyncfg feature.

To troubleshoot issues with the `smbios_memory` collector, run the `go.d.plugin` with the debug option enabled. The output
should give you clues as to why the collector isn't working.

- Navigate to the `plugins.d` directory, usually at `/usr/libexec/netdata/plugins.d/`. If that's not the case on
  your system, open `netdata.conf` and look for the `plugins` setting under `[directories]`.

  ```bash
  cd /usr/libexec/netdata/plugins.d/
  ```

- Switch to the `netdata` user.

  ```bash
  sudo -u netdata -s
  ```

- Run the `go.d.plugin` to debug the collector:

  ```bash
  ./go.d.plugin -d -m smbios_memory
  ```

  To debug a specific job:

  ```bash
  ./go.d.plugin -d -m smbios_memory -j jobName
  ```

### Getting Logs

If you're encountering problems with the `smbios_memory` collector, follow these steps to retrieve logs and identify potential issues:

- **Run the command** specific to your system (systemd, non-systemd, or Docker container).
- **Examine the output** for any warnings or error messages that might indicate issues.  These messages should provide clues about the root cause of the problem.

#### System with systemd

Use the following command to view logs generated since the last Netdata service restart:

```bash
journalctl _SYSTEMD_INVOCATION_ID="$(systemctl show --value --property=InvocationID netdata)" --namespace=netdata --grep smbios_memory
```

#### System without systemd

Locate the collector log file, typically at `/var/log/netdata/collector.log`, and use `grep` to filter for collector's name:

```bash
grep smbios_memory /var/log/netdata/collector.log
```

**Note**: This method shows logs from all restarts. Focus on the **latest entries** for troubleshooting current issues.

#### Docker Container

If your Netdata runs in a Docker container named "netdata" (replace if different), use this command:

```bash
docker logs netdata 2>&1 | grep smbios_memory
```

### Permission denied reading the DMI table

The Netdata Agent user cannot read `/sys/firmware/dmi/tables/DMI`. Grant read access to that file or run the Agent with sufficient privileges.


### No memory devices found

Some virtualized environments do not expose SMBIOS Memory Device (type 17) records. In that case there is no per-DIMM inventory to collect.
